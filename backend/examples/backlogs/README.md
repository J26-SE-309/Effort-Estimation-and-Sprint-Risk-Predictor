# Synthetic backlogs

**Synthetic data: for development, tests, demos and user-study scenarios only. Never use it to evaluate the
models** (ML guide 7.2), and name it in the proposal's AI-use disclosure (Appendix H).

Each file is a complete `POST /api/v1/estimate` request: made-up stories for a tutoring platform, with the
signals Components 1–3 would send (`upstream`) and tracker links (blockers, dependencies, epic). The service ignores
the `_synthetic` label at the top of each file.

These files are generated by `backend/app/backlogs.py` (seeded, so the same every time). Don't edit them by hand;
change the generator and run, from `backend/`:

```powershell
python -m app.devdata backlogs
```

A test fails when the files and the generator disagree.

| File | What it is for |
|---|---|
| `syn-new.json`, `syn-one.json`, `syn-two.json` | Teams with 0, 1 and 2 closed sprints: still cold starts |
| `syn-steady.json` | A predictable team: mostly clear stories with acceptance criteria |
| `syn-erratic.json` | An unpredictable team: many vague stories, more blockers |
| `syn-nopoints.json` | A team that never estimates: no story points |
| `syn-steady-without-components.json` | The steady backlog without any component signal: the service's own stand-ins (FR17) |
| `syn-steady-component-1-only.json` | Only Component 1's signals: partly degraded (FR17) |
| `edge-cases.json` | Odd stories for an unknown project: an empty description, 5,200 words, Sinhala, Tamil and emoji, 0 and 100 points, many blockers, extreme signals, odd INVEST keys, an unknown issue type |

The team backlogs are for each team's running sprint (`sprint_id`). Load the teams' sprint history first, and the
estimates use it:

```powershell
python -m app.devdata load --synthetic
```

To try one, open http://localhost:8004/docs and paste a file into `POST /api/v1/estimate`, or send it with curl:

```bash
curl -X POST http://localhost:8004/api/v1/estimate -H "Content-Type: application/json" --data-binary @syn-steady.json
```

Stories come in five kinds, and their signals follow the kind, with some noise:

| Kind | Story | Signals |
|---|---|---|
| clear | "As a … I want … so that …", with Given/When/Then criteria | Low ambiguity, high acceptance-criteria completeness, all INVEST flags |
| partial | The same form, with one criterion or none | Middling scores |
| vague | "Improve the booking page … Details TBD." | High ambiguity, vague terms, missing information, no criteria |
| bug | Steps to reproduce, sometimes a stack trace | Low ambiguity, no criteria, testable |
| task | Technical work | Low ambiguity, no criteria |

Traceability always matches the links: coverage is the share of *has an epic*, *has linked issues* and *has linked
tests*, and a blocked story is never INVEST-independent.
